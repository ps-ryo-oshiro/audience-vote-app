# Requirements Document

## Project Description (Input)

### 誰の問題か
オーディエンス投票の来場者（投票者）。

### 現状
投票は1人1票で、一度送信すると投票完了画面が表示されたまま、その端末からは二度と投票できない。二重投票の防止は次の2段で行われている。

- 端末側: `localStorage` の `audience-vote-submitted` フラグ
- サーバー側: Cloudflare Workers KV に `voter:{voterToken}` を記録し、2回目は 409 を返す

そのため、投票受付中であっても「押し間違えた」「他のアプリを見てから決め直したい」という場合に、投票をやり直す手段がまったくない。運営側にも特定の票だけを取り消す手段がない。

なお票の保存先である Firebase Realtime Database は、セキュリティルールで **追記のみ許可・削除と上書きを禁止** している。これは認証を一切使わない設計における唯一の整合性の防御線であり、緩めない前提とする。したがって「前の票をDBから物理削除する」方式は採用できない。

### 何を変えたいか
投票受付が開いている間に限り、投票者が自分の投票をやり直せるようにする。

- 投票完了画面に「やり直す」ボタンを置く
- 押すとアプリ一覧に戻り、選択状態は解除された状態から選び直せる
- やり直した結果、その投票者の票は**最後に選んだ1件だけ**が集計に反映される（前の票は集計対象外になる）
- やり直せる回数に上限は設けない（受付中は何度でも選び直せる）
- 投票受付が停止された後はやり直せない

### 決定済みの方針
- 前の票はDBから削除せず、追記のまま残す。集計側で「同一投票者の最新票だけを有効とする」ことで、利用者からは「やり直し」に見える挙動を実現する
- `voterToken` は再生成しない（再生成すると前の票を無効化できず票数が増えてしまう）
- `votes` に保存する `voterToken` のハッシュ化は、本仕様では対象外とする（社内イベント限定のためリスクを受容する。ただし既知のリスクとして記録する）

### 改訂履歴
- 2026-09-11 初版
- 2026-09-11 改訂1: やり直し回数の上限（3回）を撤廃し、受付中は何度でもやり直せる方針に変更。上限が担っていた「他人の票を書き換える攻撃の被害上限」が失われることを受容リスクとして明記する

## Introduction

本仕様は、audience-vote-app において、投票受付中に限り投票者が自分の投票をやり直せるようにする機能を対象とする。

既存の票の保存先は「追記のみ許可・削除と上書きを禁止」という制約下にあり、この制約は認証を使わない設計における唯一の整合性の防御線であるため維持する。したがって本機能は、過去の票を物理的に消すのではなく、**同一投票者の最新の票だけを有効票として集計する**ことで、投票者から見て「やり直し」に見える挙動を実現する。あわせて、やり直しによって集計が二重計上されないことと、受付停止後はやり直せないことを定める。

## Boundary Context

- **In scope**:
  - 投票完了画面からのやり直し操作と、アプリ一覧への復帰
  - 受付中は回数に上限を設けずにやり直せること
  - 投票受付が停止している場合のやり直しの抑止
  - 管理画面の集計における「同一投票者の最新票のみを有効とする」判定
  - 有効票・無効票の件数の提示
  - やり直しの回数にかかわらず「1人1票」を保つこと
  - 過去の投票記録を削除・変更しないこと

- **Out of scope**:
  - やり直し回数の上限。本仕様では設けない
  - 投票記録に保存される投票者識別子の秘匿化（ハッシュ化）。本仕様では対応せず、既知のリスクとして記録する
  - 管理画面からの個別の票の取り消し・編集
  - 来場者・管理者のログイン認証
  - 投票受付停止後のやり直し
  - 過去の票の物理削除
  - 別の端末・別のブラウザからのやり直し（投票者の識別は端末に保存された識別子に依存する）
  - 投票受付状態の投票画面へのリアルタイム反映（画面を開いたまま受付状態が切り替わった場合の即時反映）

- **Adjacent expectations**:
  - 票の保存先のセキュリティルール（追記のみ許可・削除と上書きを禁止）は変更しない
  - 既存のデータ構成（`audienceApp/teams`・`audienceApp/votes`・`audienceApp/settings`）を維持する
  - 管理画面の既存の集計表示（部門別集計・得票順の順位・同票の明示・集計対象外件数・オーディエンス賞の判定）は、有効票のみを対象とする形で従来どおり機能する
  - 投票者の端末の保存データが消去された場合は別の投票者として扱われる。これは本機能の導入前から変わらない既知の制約とする
  - 接続設定が未構成の環境（ローカル確認用のフォールバック動作）でも、本仕様で定める挙動が同じように確認できること

- **受容する既知のリスク**:
  - `votes` は誰でも読み取り可能で、投票者識別子が生の値で保存される。やり直しに回数上限を設けないため、第三者が識別子を収集して他人の票を受付中に何度でも書き換えられる。社内イベント限定であることから、本仕様ではこのリスクを受容する
  - 集計の重複排除に万一不具合があった場合、票数の水増しに上限がない。このため重複排除を通さない集計経路を作らないことを、実装上の最重要事項とする

## Requirements

### Requirement 1: 投票完了画面からのやり直し

**Objective:** As a 来場者（投票者）, I want 投票した後に自分の投票をやり直したい, so that 押し間違いや、他のアプリを見てからの気持ちの変化に対応できる

#### Acceptance Criteria

1. While 投票受付が開いている, when 投票完了画面が表示されている, the Voting Page shall 投票をやり直す操作を提供する
2. When 投票者がやり直す操作を行う, the Voting Page shall 投票完了画面を閉じ、アプリ一覧を選択可能な状態に戻す
3. When やり直しによってアプリ一覧に戻る, the Voting Page shall どのアプリも選択されていない状態にする
4. When やり直し後に投票者がアプリを選んで送信する, the Voting Page shall 最初の投票と同じ手順で送信を行い、成功時に投票完了画面を表示する
5. When やり直し後の投票が送信される, the Vote Submission Service shall その投票を、最初に投票した人と同一の投票者による投票として扱う
6. If やり直し後の投票の送信に失敗した, then the Voting Page shall 失敗した理由を投票者に示し、アプリを選び直して再度送信できる状態を保つ
### Requirement 2: やり直し回数の扱い

**Objective:** As a 来場者（投票者）, I want 投票受付が開いている間は何度でも投票をやり直したい, so that 締め切りまで納得のいく選択ができる

#### Acceptance Criteria

1. The Vote Submission Service shall 投票受付が開いている間、投票者がやり直せる回数に上限を設けない
2. While 投票受付が開いている, the Voting Page shall 投票完了画面に常にやり直す操作を提供する
3. The Vote Submission Service shall やり直しの回数にかかわらず、得票数に反映される票を投票者ごとに1件に保つ

### Requirement 3: 投票受付状態によるやり直しの制御

**Objective:** As a 運営担当者, I want 投票受付を停止した後はやり直しをできなくしたい, so that 締め切り後に集計結果が変動しない

#### Acceptance Criteria

1. While 投票受付が停止している, the Voting Page shall 投票完了画面にやり直す操作を提供しない
2. If 投票受付が停止している状態で投票の送信を受け取る, then the Vote Submission Service shall その投票を記録せず、投票受付が終了していることを投票者に示す
3. When 投票受付の終了により投票の送信が拒否される, the Voting Page shall 直前に有効だった投票がそのまま有効であることを投票者に示す
4. While 投票受付が停止している, the Voting Page shall 新たな投票の送信を受け付けない

### Requirement 4: 集計での有効票の決定

**Objective:** As a 運営担当者, I want やり直しがあっても1人1票として正しく集計したい, so that オーディエンス賞の判定が公正に行える

#### Acceptance Criteria

1. The Admin Dashboard shall 同一の投票者による複数の投票のうち、最後に行われた1件のみを得票数に数える
2. The Admin Dashboard shall やり直しによって無効になった投票を、いずれのアプリの得票数にも数えない
3. When 投票者がやり直して別のアプリに投票する, the Admin Dashboard shall 前に投票していたアプリの得票数を1件減らし、新たに投票したアプリの得票数を1件増やした結果を示す
4. When 投票者がやり直して同じアプリに投票する, the Admin Dashboard shall そのアプリの得票数を変化させない
5. The Admin Dashboard shall 総投票数として有効票の件数を示す
6. The Admin Dashboard shall やり直しによって無効になった投票の件数を、有効票と区別して示す
7. When 投票が追加される, the Admin Dashboard shall 画面を再読み込みせずに集計結果を更新する
8. The Admin Dashboard shall 部門別集計・得票順の順位・同票の明示・オーディエンス賞の判定を、有効票のみを対象として行う
9. If どのアプリにも一致しない投票が存在する, then the Admin Dashboard shall 従来どおりその投票を集計対象外として件数のみ示す

### Requirement 5: 投票記録の保全

**Objective:** As a 運営担当者, I want やり直しがあっても過去の投票記録が失われないようにしたい, so that 集計結果に疑義が生じたときに経緯を確認できる

#### Acceptance Criteria

1. The Vote Submission Service shall やり直しの際に、過去に記録された投票を削除も変更もしない
2. The Vote Submission Service shall 各投票について、どの投票者によるものか、いつ行われたかを記録する
3. The Vote Submission Service shall 投票記録の保存先に対する「追記のみ許可・削除と上書きを禁止」という制約を維持する
4. When 同一の投票者による投票が複数記録されている, the Admin Dashboard shall どれが有効票であるかを一意に決定できる

### Requirement 6: 二重投票防止の維持

**Objective:** As a 運営担当者, I want やり直しを回数無制限で認めた後も、1人が複数票を投じられない状態を保ちたい, so that 投票結果の信頼性が損なわれない

#### Acceptance Criteria

1. The Vote Submission Service shall 1人の投票者が得票数に反映させられる票を、常に1件までとする
2. If 投票者がやり直し操作を経ずに投票の送信を繰り返した, then the Vote Submission Service shall やり直しと同じ扱いとし、最後の送信のみを有効票とする
3. When 投票の送信が拒否される, the Voting Page shall 拒否された理由を投票者に示す
