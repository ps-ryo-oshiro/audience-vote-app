# Implementation Plan

> 2026-09-11 改訂: やり直し回数の上限（3回）を撤廃し、受付中は何度でもやり直せる方針に変更した。

## 1. ローカル検証環境の整備

- [x] 1.1 Worker をローカルで実行し、投票の検証を行える状態にする
  - シェルの Node.js を v22 系に切り替える（wrangler v4 は v22 以上を要求する。既定が v18 のままだと全コマンドが失敗する）
  - `.dev.vars` に投票アプリの DB URL が設定されていることを確認する
  - KV の状態をリポジトリ外のパスに永続化して起動する（`--persist-to /tmp/audience-vote-wrangler-state`）。以降の検証はこのパスを固定して使い、Worker 再起動後も回数が保持されることを確認できるようにする
  - 検証に使う表示対象チームのIDを1件以上把握する（本戦または表示中の敗者復活候補。どちらも該当がなければ、検証用チームを1件だけ表示状態にして控えておく）
  - 投票受付の開始・停止を検証中に切り替える手段を確保する（管理画面へのログイン、または受付状態への直接の書き込み）
  - 確認用に作成した票は、オーナー権限の Firebase CLI で削除する。クライアント経由の削除はルールで拒否されるため、この手段以外を使わない
  - 観測可能な完了状態: 起動ログに KV バインディングと DB URL の変数が出て、変更前の `/api/vote` に表示対象チームのIDと任意のトークンを送ると 200 が返り、その票をオーナー権限で削除できる
  - _Requirements: 2.5, 3.2_

## 2. サーバー側の投票受付制御

- [ ] 2.1 受付状態をサーバー側で検証する
  - `/api/vote` の検証順序を「リクエスト形式 → 設定の存在 → 受付状態 → 送信回数 → チームの表示対象判定 → 票の追記 → 回数の加算」に固定し、受付状態の判定を最初期に置く
  - 受付が停止していれば票を記録せず 403 を返す。エラーコードは表示対象外チームの拒否と区別できる値にする
  - 受付状態が未設定の場合は受付中として扱う
  - 受付状態の読み取りに失敗した場合は票を記録せず 500 を返す
  - この判定はやり直しに限らず、初回の投票を含むすべての送信に適用する
  - 観測可能な完了状態: 受付を停止した状態で送信すると 403 が返り、票のレコードが1件も増えない。受付中に戻すと同じ送信が 200 になる
  - _Requirements: 3.2, 3.4_
  - _Boundary: VotingStatusGuard, VoteSubmissionApi_

- [ ] 2.2 送信回数の上限を判定し、残りやり直し回数を返す
  - 投票者ごとの送信回数を保存先から読み、上限（通算4回 = 初回1回 + やり直し3回）に達していれば票を記録せず 409 を返す
  - 上限の判定はチームの検証より前に行い、上限到達時にチームの読み取りを発生させない
  - 回数の判定に、投票者の端末から送られた情報を一切使わない
  - 票の追記に成功した後にだけ回数を加算して保存する（保持期間は従来どおり付け直す）。追記に失敗した送信は回数を消費しない
  - 既存の「1回送信済み」を示す保存値をそのまま1回として解釈し、データの書き換えを不要にする
  - 成功応答に、今回の送信後にあと何回やり直せるかを含める
  - 409 のエラーコードを、やり直し上限に達したことを表す値に改める（従来の二重投票を表す値から置き換える）
  - 上限の値は投票画面のフォールバック動作でも同じ値を使うため、既存の表示判定と同じ「複数箇所で揃える」旨のコメントを添える
  - 観測可能な完了状態: 同一トークンで4回送信すると残りやり直し回数が 3→2→1→0 と減り、5回目が 409 になり、5回目の送信では票のレコードが増えない
  - _Requirements: 2.1, 2.4, 5.1, 5.2, 6.2_
  - _Boundary: VoteAttemptCounter, VoteSubmissionApi_

## 3. 投票画面のやり直し

- [x] 3.1 投票完了画面にやり直す操作を表示する
  - 受付中であるときだけ、やり直す操作を描画する（受付状態の判定は、締め切り後に画面を開き直した場合に備えた防御であり、サーバー側の拒否と二重で機能する）
  - 受付中は何度でも選び直せる旨を操作に併記する
  - 完了画面の既存の配色・体裁に合わせた見た目を整える
  - 観測可能な完了状態: 投票直後の完了画面にやり直す操作が表示され、受付停止中に開いた画面では表示されない
  - _Requirements: 1.1, 2.2, 3.1_
  - _Boundary: VoteCompletionOverlay_

- [x] 3.2 やり直し操作でアプリ一覧に戻す状態遷移を実装する
  - やり直し操作で、完了画面の要素を DOM から取り除く（既存の完了画面が残っていると再表示できないため）
  - 端末に保存された投票済みフラグを削除し、送信ガードと起動時のロックの両方を通る状態に戻す
  - 選択されていたアプリの選択を解除する
  - 投票者の識別子は再生成せず、端末に保存された値をそのまま使い続ける
  - 再送信は既存の送信経路をそのまま通す（やり直し専用の送信処理を作らない）
  - 観測可能な完了状態: やり直す操作を押すとアプリ一覧に戻り、どのアプリも選択されておらず、選び直して送信すると完了画面が再表示される。この間に端末に保存された投票者の識別子が変化しない
  - _Requirements: 1.2, 1.3, 1.4, 1.5_
  - _Boundary: VoteFlowController_

- [x] 3.3 送信が拒否された理由ごとに画面状態を分ける
  - 分岐は HTTP のステータスではなくサーバーが返すエラーコードで行う（403 は受付終了と表示対象外チームの双方で使われるため、ステータスだけでは区別できない）
  - 受付終了による拒否では投票済み状態に戻し、直前の投票が有効である旨を示す
  - それ以外の失敗では未投票状態に戻し、選択を保ったまま再送信できる状態を保つ
  - 観測可能な完了状態: 受付停止中にやり直して送信すると受付終了のメッセージが出、通信エラー時は選択が保たれたまま再送信できる
  - _Requirements: 1.6, 3.3, 6.3_
  - _Boundary: VoteFlowController_

- [x] 3.4 接続設定なしのフォールバック動作でも何度でもやり直せるようにする
  - ブラウザ内に保存された票の件数による送信の拒否を行わない
  - 観測可能な完了状態: 接続設定を外した状態でも、受付中は何度でもやり直して送信できる
  - _Requirements: 2.1_
  - _Boundary: VoteFlowController_

## 4. 管理画面の集計

- [x] 4.1 (P) 同一投票者の最新票を選ぶ処理を追加する
  - タスク2・3と並行して着手できる（触れるのは管理画面のスクリプトのみで、投票画面・Worker のファイルに手を入れない）
  - 票の購読でレコードのキーを保持するように変更する（現状はキーを捨てているため、同時刻の票の順序を決められない）
  - フォールバック動作では、ブラウザ内に保存された票の並び順の位置をキーとして付与する
  - 同一投票者の票のうち、投票時刻が最新のものを有効票とし、同時刻ならキーの大きいものを選ぶ
  - 投票者の識別子を持たない票は、他のいずれとも同一視せず、それぞれ独立した有効票として扱う
  - 選ばれなかった票の件数を、やり直しにより無効になった件数として返す
  - 観測可能な完了状態: 同一投票者の票を複数含むデータを流し込むと、有効票が投票者ごとに1件だけになり、有効票数と無効票数の合計が全票数に一致する
  - _Requirements: 2.3, 4.1, 4.2, 5.4, 6.1, 6.2_
  - _Boundary: EffectiveVoteSelector_

- [x] 4.2 集計の入口を有効票に一本化する
  - 再集計の入口で有効票を1度だけ選び、部門別集計・全体集計・受賞候補判定のすべてに同じ結果を渡す
  - 個々の描画処理は有効票を受け取る前提とし、内部で再度の絞り込みを行わない（絞り込みを経由しない集計経路を1つも残さないことが、二重計上を防ぐ唯一の担保になる）
  - どのチームにも一致しない票の扱いは従来どおりとし、有効票の中から数える
  - 既存の自動更新（画面を再読み込みせずに集計へ反映される動き）を壊さない
  - 観測可能な完了状態: やり直して別のアプリに投票すると、前のアプリの得票が1減り新しいアプリが1増え、順位と受賞候補も同じ結果に追従する
  - _Requirements: 4.3, 4.4, 4.7, 4.8, 4.9_
  - _Boundary: VoteAggregator_

- [x] 4.3 総票数と無効票の件数を提示する
  - 総票数に有効票の件数を表示する
  - やり直しにより無効になった票の件数を、有効票と区別できる形で併記する表示要素を追加する
  - 無効票が0件のときは併記を表示しない
  - 観測可能な完了状態: やり直しを1回行った状態で総票数が増えず、無効票1件が別枠で表示される
  - _Requirements: 4.5, 4.6_
  - _Boundary: VoteAggregator_

## 5. 結合確認

- [x] 5.1 Worker の投票APIを確認する
  - 同一トークンで連続送信（例で6回）してもすべて受け付けられ、回数による拒否が起きないことを確認する
  - 受付停止中の送信が拒否され、票が増えないことを確認する
  - 受付を戻すと同じ送信が受け付けられることを確認する
  - 票の保存先のルール定義に差分がないことを確認する
  - 観測可能な完了状態: 上記すべてが期待どおりの応答になり、確認用に作成した票をオーナー権限で削除した状態で終わる
  - _Requirements: 2.1, 3.2, 5.1, 5.2, 5.3, 6.2_

- [ ] 5.2 投票画面のやり直しを通しで確認する
  - 投票 → やり直す → 選び直して再送信 の一連を 4回以上繰り返し、都度受け付けられることを確認する
  - やり直し後の完了画面にも、引き続きやり直す操作が表示されることを確認する
  - 完了画面を表示したまま管理画面で受付を停止し、やり直して送信したときに受付終了のメッセージが出て、直前の投票が有効である旨が示されることを確認する（受付状態のクライアント側判定とサーバー側の拒否が二重で機能していることの実効確認）
  - 受付停止後に開いた画面でやり直す操作が出ないことを確認する
  - 観測可能な完了状態: 上記すべてが期待どおりに見え、送信が失敗したときは選択を保ったまま再送信できる
  - _Requirements: 1.1, 1.2, 1.3, 1.4, 1.5, 1.6, 2.1, 2.2, 3.1, 3.3, 6.3_

- [ ] 5.3 管理画面の集計を確認する
  - 2台（またはプライベートウィンドウ）で別々のアプリに投票した状態から、1台がやり直して別のアプリに投票する
  - 同じアプリにやり直した場合に、得票数が変わらず無効票だけが増えることを確認する
  - やり直しを挟んで同票の状態を作り、受賞候補が同票として両チームを示すことを確認する
  - 存在しないチームIDの票を混ぜ、従来どおり集計対象外として件数のみ示されることを確認する
  - 観測可能な完了状態: 総票数が投票した人数と一致し、無効票の件数が別枠で正しく示され、画面を再読み込みせずに更新される
  - _Requirements: 4.1, 4.2, 4.3, 4.4, 4.5, 4.6, 4.7, 4.8, 4.9, 5.4, 6.1_

- [ ] 5.4 接続設定なしのフォールバック動作を確認する
  - ブラウザ内の保存データを消した状態から、投票とやり直しを複数回行う
  - 同じ状態の管理画面で、集計が接続時と同じ規則（最新票のみ有効・無効票は別枠）で表示されることを確認する
  - 観測可能な完了状態: フォールバック動作でも何度でもやり直せ、集計に無効票が計上されない
  - _Requirements: 2.1, 4.1, 4.5, 4.6_
