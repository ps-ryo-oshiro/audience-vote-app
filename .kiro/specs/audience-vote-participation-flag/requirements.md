# Requirements Document

## Project Description (Input)
社内AIコンテスト「AI爆速アプリコンテスト」本審査（2026/9/12土）のオーディエンス投票アプリで、本戦確定12チームに加えて、当日会場に観覧参加した予選落選チーム（敗者復活枠）を投票対象に加えられるようにする。エントリーチームとアプリ名は事前に分かっているため、全48チームを事前に登録しておく。本戦確定12チームは常に投票画面に表示し、敗者復活候補のチームは当日、管理画面で表示・非表示を切り替える（観覧に来なかったチームは非表示のまま）。投票画面・集計上は本戦チームと敗者復活枠チームを区別しない。あわせて、既存実装で判明した投票データ未保存・二重投票防止未実効などの本番稼働の必須修正も対応する。

### 改訂履歴
- 2026-09-10 初版（`--auto` 生成）
- 2026-09-10 改訂1: 以下の決定事項を反映

    - 同居案は、審査データを守るためのアクセス制限により審査サイトが閲覧・評価変更できなくなるため不採用とした
  - 来場者・管理者ともに認証（ログインサービスによる本人確認）は一切使わない
  - 紹介動画URLは後日提供されるため、未設定のまま登録・運用できるようにする
  - 接続設定の実値はリポジトリに含めない

  - 管理画面のCSV/Excel取込を廃止する。チームは審査アプリのデータから開発担当者が事前に一括登録し、紹介動画URLや名称の修正も同じ手順で追記する
  - 本戦確定12チームは常に表示し、管理画面での切替対象は敗者復活候補（本戦確定以外）のチームに限る
  - 投票画面にエントリーNoを表示し、部門ごとにエントリーNo順で並べる

## Introduction
本仕様は、audience-vote-appにおいて、敗者復活候補のチームを投票対象に含めるかどうかを運営担当者が当日制御できる機能と、その機能が実運用で正しく動くために必要な既存バグ修正（投票データ永続化、二重投票防止、管理操作の書き込み整合性）を対象とする。あわせて、投票アプリ専用データストアの用意と、審査アプリのデータストアを変更せずにチームデータを流用して事前登録するための要件を定める。

## Boundary Context (Optional)
- **In scope**: 全48チームの事前登録（審査アプリのデータを元に）と、紹介動画URL・名称の追記・修正、本戦確定チームの常時表示、敗者復活候補チームの表示切替UI、投票画面での表示チームの絞り込みとエントリーNoの表示、オーディエンス賞集計、投票データのサーバー側永続化とチーム検証、二重投票防止の実効化、認証なしでの管理操作の書き込み整合性、投票アプリ専用データストアの用意と審査アプリへの非干渉、接続設定の秘匿管理、紹介動画URL未設定での運用、同時接続数上限への配慮
- **Out of scope**: 来場者・管理者のログイン認証（Googleログイン、匿名認証などの本人確認サービス）、管理画面からのチームの追加・削除・名称編集・ファイル取込、投票画面での本戦確定チームと敗者復活枠チームの見た目上の区別表示、部門賞・総合グランプリなどオーディエンス賞以外の審査ロジック、審査アプリ自体の機能・データ・アクセス設定の変更、投票結果のリアルタイム反映（ライブ更新）、独自ドメイン設定、CI/CD自動化
- **Adjacent expectations**:
  - 既存のデータ構成（`audienceApp/teams`, `audienceApp/votes`, `audienceApp/settings`）を維持すること
  - 審査アプリ（judge-app）のデータストアは、チーム一覧（エントリーNo・アプリ名・部門）の読み取り元としてのみ扱う。審査サイトの閲覧・評価変更は本仕様の前後で変わらないこと
  - 本戦確定12チームのエントリーNo一覧は、運営側から提供される
  - 紹介動画URLは運営側（寺司さん）から後日、エントリーNo（またはアプリ名）とURLの一覧で提供される

## Requirements

### Requirement 1: チームの区分と表示状態
**Objective:** As a 運営担当者, I want 各チームが本戦確定か敗者復活候補かを区別し、投票画面に表示するかどうかの状態を持たせたい, so that 本戦チームを確実に表示しつつ、観覧に来た敗者復活候補だけを投票対象に加えられる

#### Acceptance Criteria
1. The Team Management Service shall 各チームに、エントリーNo・部門・アプリ名・紹介動画URL・区分（本戦確定／敗者復活候補）・表示状態（表示する／表示しない）を保持する
2. The Team Management Service shall 本戦確定チームの表示状態を常に「表示する」とする
3. When 敗者復活候補のチームが登録される, the Team Management Service shall 表示状態を「表示しない」で初期化する
4. If チームの表示状態が未設定である, then the Team Management Service shall そのチームを「表示しない」として扱う

### Requirement 2: チームの事前一括登録
**Objective:** As a 運営担当者, I want 事前審査で使ったエントリーチームとアプリ名をそのまま投票アプリに一括登録したい, so that 当日は敗者復活候補の表示切替だけで済み、チーム名の二重入力や転記ミスも避けられる

#### Acceptance Criteria
1. The 登録手順 shall 審査アプリに登録済みの全48チームを、エントリーNo・部門・アプリ名を保ったまま投票アプリのチームとして登録する
2. When 本戦確定チームのエントリーNo一覧を指定して登録する, the 登録手順 shall 指定されたチームを本戦確定、それ以外を敗者復活候補として登録する
3. When 同じチームを含む登録を再度実行する, the 登録手順 shall 同じエントリーNoのチームを重複登録せず、既存チームの敗者復活候補としての表示状態と紹介動画URLを変更しない
4. When 審査アプリのチームデータを読み取る, the 登録手順 shall 審査アプリのデータを読み取りのみで扱い、変更しない
5. If 審査アプリの部門名が投票アプリの部門（ライフ・ワーク・ローカル）のいずれにも対応しない、または本戦確定に指定したエントリーNoが存在しない, then the 登録手順 shall 該当チームを登録せず、該当するエントリーNoを一覧で提示する
6. The Admin Dashboard shall チームの追加・削除やファイル取込の機能を提供しない

### Requirement 3: 敗者復活候補の当日の表示切替
**Objective:** As a 運営担当者, I want 管理画面から敗者復活候補のチームを1チームずつ表示・非表示に切り替えたい, so that 観覧に来たチームだけを当日すぐに投票対象へ加えられる

#### Acceptance Criteria
1. The Admin Dashboard shall 敗者復活候補の全チームについて、エントリーNo順に、表示状態を切り替える操作を提供する
2. The Admin Dashboard shall 本戦確定チームには表示状態の切替操作を提供せず、本戦確定で常に表示されることが分かる形で示す
3. The Admin Dashboard shall 現在表示中の敗者復活候補チームの数を示す
4. When 運営担当者が敗者復活候補チームの表示状態を切り替える, the Admin Dashboard shall 画面全体を再読み込みせずに変更後の状態を示す
5. When 表示状態の切替操作が行われる, the Team Management Service shall 変更後の状態を永続化する
6. If 表示状態の保存に失敗した, then the Admin Dashboard shall 切替操作を元の状態に戻し、失敗したことを運営担当者に示す

### Requirement 4: 投票画面での表示
**Objective:** As a 来場者（投票者）, I want 当日投票対象になっているチームだけを、分かりやすい順番で見て投票したい, so that 発表で聞いたチームをすぐに見つけ、誤って対象外のチームに投票しないで済む

#### Acceptance Criteria
1. The Voting Page shall 表示状態が「表示する」であるチームのみを一覧表示する
2. If チームの表示状態が「表示しない」または未設定である, then the Voting Page shall そのチームを一覧に表示しない
3. The Voting Page shall 本戦確定チームと敗者復活枠チームを同一の一覧内で区別なく表示する
4. If チームの紹介動画URLが未設定である, then the Voting Page shall そのチームの紹介動画リンクを表示せず、チームを投票対象として選択可能なまま表示する
5. The Voting Page shall 来場者にログイン・本人確認を求めずに投票を受け付ける
6. The Voting Page shall 各チームのエントリーNoをアプリ名と併せて表示する（例: 「No.1 MedRecall」）
7. The Voting Page shall 部門ごとに、チームをエントリーNoの小さい順に並べる

### Requirement 5: オーディエンス賞集計への反映
**Objective:** As a 運営担当者, I want 投票対象になった全チームの得票を同列に集計したい, so that 敗者復活枠チームも公平にオーディエンス賞の対象になる

#### Acceptance Criteria
1. The Admin Dashboard shall 表示状態にかかわらず、登録済みの全チームの得票数を部門別・全体集計に表示する
2. The Admin Dashboard shall 得票数が最多のチームを、本戦確定チームと敗者復活枠チームの区別なくオーディエンス賞候補として提示する

### Requirement 6: 投票データの受付と検証
**Objective:** As a 運営担当者, I want 投票時に不正・無効な投票を排除して正しく集計したい, so that オーディエンス賞の結果に信頼性を持たせられる

#### Acceptance Criteria
1. When 投票リクエストを受け付ける, the Voting API shall 送信されたチームIDが登録済みチームとして実在するか検証する
2. If 送信されたチームIDが実在しない, then the Voting API shall 投票を拒否し、エラーを返す
3. If 送信されたチームIDの表示状態が「表示しない」である, then the Voting API shall 投票を拒否し、エラーを返す
4. When 有効な投票を受け付ける, the Voting API shall 投票内容（対象チーム）を集計対象データとして永続化する

### Requirement 7: 二重投票の防止
**Objective:** As a 運営担当者, I want 同じ端末からの重複投票を防ぎたい, so that 1人1票の原則を守り集計の公平性を保てる

#### Acceptance Criteria
1. When 同一の投票者トークンから2回目の投票リクエストが送信される, the Voting API shall 投票を拒否する
2. The Voting API shall 投票者トークンごとの投票済み状態を、アプリケーションの実行環境の再起動をまたいで保持する

### Requirement 8: 認証なしでの管理操作の書き込み整合性
**Objective:** As a 運営担当者, I want ログインサービスの設定なしで、管理画面からの表示切替・投票受付ON/OFF・集計閲覧が確実に動いてほしい, so that 当日の運用操作が失敗せず、事前の外部設定作業も増えない

#### Acceptance Criteria
1. When 運営担当者が管理画面で管理操作（敗者復活候補の表示切替・投票受付切替）を行う, the Team Management Service shall ログインサービスによる認証を行わずに、その操作をデータストアへの書き込み権限エラーなく完了させる
2. When 運営担当者が管理画面で集計を表示する, the Admin Dashboard shall ログインサービスによる認証を行わずに、全投票データを読み取って集計を表示する
3. The Voting Page shall 投票受付が停止中である場合、投票フォームへの入力を無効化する

### Requirement 9: 管理画面の入室パスワード
**Objective:** As a 運営担当者, I want 本番公開前に管理画面の入室ID・パスワードを初期値から変更したい, so that 来場者が管理画面を誤って・興味本位で操作しにくくする

#### Acceptance Criteria
1. The Admin Dashboard shall 本番公開時点で、初期状態のデモ用ID・パスワード（`admin`/`admin123`）以外の値で入室を判定する
2. If 入室時のID・パスワードの組み合わせが一致しない, then the Admin Dashboard shall 入室を拒否しエラーメッセージを表示する

> 注: この入室チェックは画面上の目隠しであり、データストアへの直接アクセスは防がない（「既知のリスク」参照）。値の変更はユーザー指示により本番公開直前まで保留とする。

### Requirement 10: 投票アプリ専用データストアと審査アプリへの非干渉
**Objective:** As a 運営担当者, I want 投票アプリを審査アプリとは別のデータストアで動かしたい, so that 審査サイトの閲覧・評価変更を今までどおり使えるまま、事前審査の記録（採点）を来場者の目に触れさせずに済む

#### Acceptance Criteria
1. The Data Store shall 投票アプリのデータ（チーム・投票・受付設定）を、審査アプリとは別の投票アプリ専用データストアに保存する
2. The Voting Page shall 来場者に配布する画面・ファイルに、審査アプリのデータストアの所在（URL・接続値）を含めない
3. The 運用手順 shall 審査アプリのデータストアの値およびアクセス設定を変更しない（読み取りのみ）
4. When 投票アプリの本番接続が完了した, the 運用手順 shall 審査サイトが従来どおり閲覧・評価変更できる状態であること（審査アプリのアクセス設定が変わっていないこと）を確認する
5. The 投票アプリ専用データストア shall 投票アプリの領域（チーム・投票・受付設定）以外への読み書きを拒否する

### Requirement 11: 接続設定の秘匿管理
**Objective:** As a 開発担当者, I want データストアの接続値をリポジトリに含めずに運用したい, so that 公開リポジトリ上に接続値が残らない

#### Acceptance Criteria
1. The Repository shall データストアの実際の接続値を含むファイルをバージョン管理の対象外とする
2. The Repository shall 接続設定の項目名のみを記載したひな形ファイルを含み、新しい担当者がひな形から接続設定を作成できるようにする
3. When 開発担当者が手元の接続設定を置いた状態でデプロイする, the Deployment shall 手元の接続設定を公開環境に反映する
4. The Voting API shall 投票画面・管理画面と同じデータストアに対して検証・保存を行う
5. If 接続設定ファイルが存在しない, then the Voting Page shall 端末内保存（デモモード）で動作し、エラーで画面が停止しない

### Requirement 12: 登録済みチーム情報の追記・修正
**Objective:** As a 運営担当者, I want 後から届く紹介動画URLや、見つかった名称の誤りを登録済みチームに反映したい, so that 当日までに情報を揃えられ、当日の表示状態を崩さずに済む

#### Acceptance Criteria
1. When エントリーNoまたはアプリ名と紹介動画URLの一覧を反映する, the 登録手順 shall 一致するチームの紹介動画URLのみを更新する
2. When チーム情報の追記・修正を反映する, the 登録手順 shall 対象チームの区分と表示状態を変更しない
3. If 一覧の行に一致するチームがない, then the 登録手順 shall その行を反映せず、該当する行を一覧で提示する
4. When 開発担当者が特定チームのアプリ名の誤りを修正する, the 登録手順 shall そのチームのアプリ名のみを更新する

### Requirement 13: 同時接続数の上限への配慮
**Objective:** As a 運営担当者, I want 来場者約100人が一斉に投票ページを開いても管理画面が使える状態を保ちたい, so that 投票中に集計確認や受付ON/OFFができなくなる事態を避けられる

#### Acceptance Criteria
1. When 投票画面が表示に必要なデータ（チーム一覧・受付状態）を読み込み終えた, the Voting Page shall データストアとの常時接続を保持しない
2. While 来場者約100人が投票画面を開いている, the Admin Dashboard shall データストアに接続して管理操作と集計表示を行える
3. If 投票画面の表示データの読み込みに失敗した, then the Voting Page shall 再読み込みを促すメッセージを表示する

## 既知のリスク（本仕様では対策しない）
本審査までの期間（2日弱）と賞の規模を踏まえ、以下は許容する。対策は本審査後に別仕様で扱う。

1. **投票アプリ領域への直接書き込み**: データストアのURLは投票画面から誰でも知ることができ、認証を使わないため、画面やVoting APIを通さずに投票アプリの領域（チーム・投票・受付設定）を直接書き換えられる。偽の票の投入、表示状態や受付状態の改変が起こりうる
2. **途中経過の閲覧**: 認証を使わないため、投票期間中でも誰でも全投票データを読み取れる
3. **管理画面の入室チェック**: ID・パスワードは画面上の判定のみで、値も配布ファイルから読める
4. **ページ読み込み後の変更**: 投票画面は読み込み時点のチーム一覧・受付状態を表示するため、当日途中で表示状態や受付状態を変更しても、既に開いている端末には再読み込みまで反映されない
5. **登録・修正の属人化**: チームの登録・情報の追記は、投票アプリ専用データストアのオーナー（照屋さん）の端末からの操作に依存する

いずれも影響範囲は投票アプリ専用データストア内に限られ、審査データには及ばない（Requirement 10）。

緩和策（運用）: 投票終了後、集計結果を画面キャプチャ等で保存し、不自然な得票の偏りがないかを確認する。敗者復活チームの表示切替と投票受付の開始は、投票開始のアナウンス前に済ませ、アナウンス時に「開いている方は再読み込みしてください」と案内する。
